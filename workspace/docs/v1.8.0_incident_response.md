# v1.8.0 Incident Response Guide

> **适用范围**: auto_fixer 失效、B 线稳态破裂、合入后异常
> **严重度定义**: P0(灾难) / P1(严重) / P2(一般) / P3(通知)

---

## P0: 系统完全不可用（pass_rate = 0）

**触发条件**: 合入 auto_fixer 后 orchestrator 全部 check 失败

**响应**:
1. 立即执行回滚：`git revert HEAD --no-edit && git tag v1.8.0-emergency-rollback`
2. 重启网关 → 检查 `data/runs/latest_eval.json` → 确认 pass_rate 恢复到 1.0
3. 从 `data/backups/` 恢复所有配置
4. 发通知给老板："v1.8.0 P0 回滚完成。根因：...（填写）"

## P1: auto_fixer 修复失败（post_repair_pass_rate < pre_repair_pass_rate）

**触发条件**: `should_rollback()` 返回 True

**响应**:
1. 确认回滚已自动执行（auto_rollback.ps1 触发）
2. 检查 `data/runs/violations.jsonl` 查看修复日志
3. 手动检查 auto_fixer 写入的配置文件是否有语义错误
4. 将失败的 fail_reason 手动追加到 `data/evals/hardcases.jsonl` 以触发进化

## P2: 重复率 < 50% 但 inject 停止增长

**触发条件**: `evolution_status.json` 中 `injected_count` 停止增长 > 2 小时

**响应**:
1. 检查 `hardcases.jsonl` 确认是否真正饱和
2. 如果是饱和行为（4类各1条）→ 静默，预期行为
3. 如果 `blocked=True` 且 `repeat_rate≥50%` → 升级为 P1

## P3: 监控报警误报 / 日志文件变大

**触发条件**: violations.jsonl > 10MB 或监控日志增长异常

**响应**:
1. 检查日志格式是否循环（每条增行，非覆写）
2. 如果是预期增长 → 配置日志轮转（暂不实施，记入 v1.9 计划）
3. 如果包含敏感数据泄露 → 立即通知老板
